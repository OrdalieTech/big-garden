# Decisions that amend docs/PLAN.md

PLAN.md is the contract. Each entry below changes it on purpose; anything not listed here follows the plan exactly. New amendments go at the end, with the invariant or measurement that justifies them.

## D1. Local SQLite runs with `synchronous=OFF`

Every session cache directory is discarded when a process starts (PLAN §9.3). The warm tier (D21) keeps files across processes, but only as hints: a warm file is served only after the gate of a cold restore (full checksum equal to the head's, `_state_meta`, `integrity_check`), so a file torn by an OS crash fails it and the entity activates cold. An fsync would only protect against an OS crash, and nothing local is trusted after one. Durability comes from S3 alone, so the WAL and checkpoint fsyncs are dropped from every mutation. Staging files are not fsynced either.

## D2. Capture reads pages through SQLite, not through a hand-written WAL parser

After the `wal_checkpoint(TRUNCATE)` that ends each publication, the WAL holds only frames written since. Capture takes the page numbers from the WAL frame headers. That set is a superset of the pages the batch changed, since every page write in WAL mode lands in a frame. Capture then reads each page's committed content via `SELECT data FROM sqlite_dbpage WHERE pgno=?` on the library's own connection, and the final size via `PRAGMA page_count`. A page from a rolled-back frame comes back unchanged, which is harmless. Pages above `page_count` are dropped. This replaces PLAN §6.2's salt, checksum and commit-marker parser (budgeted at 350 lines) with SQLite's own pager. The authorizer allows `sqlite_dbpage` only in library mode.

To discard speculative local state, close the connection, delete `-wal`/`-shm` and reopen. The main file always equals the last published image, because a checkpoint runs only after publication.

## D3. One resolution function and hedged writes instead of "one physical attempt"

PLAN §8.1 forbids SDK retries on the head CAS so that a retried attempt cannot produce a misleading 412. That rule still holds: the SDK makes exactly one attempt per call. The library may send an explicit hedge, an identical second request with the same bytes and the same `If-Match`/`If-None-Match`, once the first has been outstanding longer than a hedge delay. This addresses the measured Scaleway PUT stalls (about 1 in 300 PUTs stall around 30 s).

Any CAS outcome other than a known success, including 412, timeout, 5xx and cancellation, goes through a single `resolve(candidate)` step:

1. GET the head.
2. If the head's nonce equals the candidate's, the write is committed.
3. If the head's revision is greater than the candidate's base, the candidate is dead (its If-Match token can never match again), and the receipt is checked in the new image.
4. If the head is still at the candidate's base, the outcome stays unknown. In that case, either fence with a no-op CAS or return `outcome_unknown`.

Immutable PUTs can be hedged and retried freely, because the key and bytes are fixed.

## D4. A Node takes over automatically from its own previous sessions

When a head's owner has this Node's NodeID but a different Session, it belongs to an earlier process of the same node. Update, Read and Lookup then take over implicitly; the CAS still fences that process. Owners with other NodeIDs still require an explicit `Takeover`. This removes boilerplate from single-node deployments.

## D5. A Create interrupted between birth and head can be resumed

If `birth.json` exists without `head.json`, and the retry carries the same operation ID and bound input hash as the birth record, the retry may build and publish genesis. The first attempt was never acknowledged, so this is the retry contract of `outcome_unknown`. Any other request still gets `state_missing`. Before resuming, the entity prefix must contain no artifact with a base revision above 0. Otherwise the head was deleted after use, and the library fails closed.

## D6. Receipt retention defaults to 1 hour

The minimum stays at 1 hour. With a 24 hour default, a hot entity at 10 writes/s accumulates about 864k receipts a day and exhausts the 64 MiB cap.

## D7. Strong reads revalidate the head with a conditional GET

`If-None-Match: <cached ETag>` answering 304 means the cached head is still current at that instant, which is the read's linearization point. A 304 has no body, so this saves bytes without weakening any guarantee.

## D8. Structure: straight-line operations, no implicit state machines

Every public operation is one function that runs top to bottom under the entity's mutex. Durable state lives in the head and the SQLite image. The in-memory entity struct holds only the cached head, its ETag, the open connection, and an `unresolved *candidate` pointer that blocks admission while it is set. There is no status enum with scattered transitions. Failure handling does not attempt in-place repair: close the cache, rehydrate from the current head, or return a typed error.

## D9. Package layout

- `/` (package `garden`): the public API, node, entity operations, maintenance.
- `internal/head`: strict codecs and invariants for namespace, birth and head JSON.
- `internal/engine`: the SQLite connection, authorizer scope, capture, the LTX adapter and restore.
- `internal/store`: the private storage interface and the S3 adapter.
- `internal/storetest`: an in-memory store with a scheduled-fault store. It is imported only by tests and qualification code.
- `internal/qual/...`: the model checker, the `qual` command and the minimal consumer.

The layout lets parallel workstreams compile and test independently. The production LOC budget in PLAN §12.1 still covers everything outside `internal/storetest` and `internal/qual`.

## D10. Speculative local state is discarded with the whole cache file

M0 (`TestCloseCheckpointsWAL`) shows that closing the last SQLite connection checkpoints committed WAL frames into the main file even with `wal_autocheckpoint=0`, and modernc v1.61.1 exposes no `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE`. The second paragraph of D2 ("close, delete `-wal`/`-shm`, reopen") would therefore install unpublished pages into the main file. Discarding speculative state (any publication that is not proven committed, quarantine, a bad connection) closes the connection and deletes the database, `-wal` and `-shm` files; the next access rehydrates from the current head. `Evict` also deletes the files. This is D8's close-and-rehydrate. A settled, closed file may be reopened only through the warm tier (D21), after the cold restore's gate.

## D11. Create runs the callback before writing birth.json

PLAN §6.3 writes `birth.json` first and runs the callback after. A callback that fails deterministically would then leave a birth without a head, which D5 lets only the identical request resume: the key would answer `state_missing` forever. Create therefore builds the genesis image locally first (speculative, never published), writes `birth.json` only after the callback succeeded, and publishes only if it won that conditional create. "Only the birth winner publishes genesis" still holds.

## D12. The D3 fence re-proposes the candidate with a fresh nonce

When `resolve` finds the head still at the candidate's base, it sends the same proposed head again with a new nonce and the same `If-Match` (or `If-None-Match: *` for genesis). All proposals of one candidate share one condition, so at most one applies; resolution accepts any of their nonces. A winning re-proposal both fences the earlier ambiguous request and commits the intended effect, so an ambiguous mutation ends committed instead of rolled back. Proposals are capped per resolve call, not per candidate: a publication sends at most three (its CAS and two re-proposals), and each later resolve of the same candidate (the settle that starts every later operation, or Close) at most two more. A per-candidate cap would leave a candidate whose first three proposals met an outage unresolvable until restart, since resolve could then only read a head that stays at the base. Sending more proposals is safe for the same reason as sending three: they all carry the one `If-Match` (or `If-None-Match: *`), so at most one applies, and resolution accepts any nonce the candidate ever sent.

## D13. LTX is pinned at v0.5.3

PLAN §1.3 names v0.5.2 as the candidate pin. v0.5.3 rejects bytes after the trailer, validates the page index against the decoded pages while streaming it instead of reading the whole tail into memory, and aborts the encoder on partial writes. The only format-relevant change excludes the SQLite lock page from checksums, and that page (262145 at 4 KiB) lies beyond the 256 MiB ceiling. Its `encoder.go` is the main-branch blob the plan inspected [S12]. Details in `research.lock.json`.

## D14. A deleted head is outside the fail-closed guarantee while a create of that key is in flight

The M1 model (finding F1, `.work/model-findings.md`, fixture `internal/qual/model/testdata/findings`) shows that a genesis CAS can apply after an administrator deletes `head.json`: `If-None-Match: *` holds again once the key is gone, and a hedge, a late-applied request, a D12 re-proposal or a D5 resume can still carry that condition. Genesis then republishes over acknowledged data. This is inherent to per-key S3 conditions and already existed in PLAN §6.3 (a single-attempt genesis CAS can apply late), so narrowing D5 or D12 would only make it rarer. G6's missing-head clause therefore holds for a head that disappears while no create of that key is in flight, and PLAN §3.3 already excludes head deletion from the store contract. The library never deletes `head.json`, `birth.json` or `namespace.json`, and the operational guide requires a bucket policy that denies `DeleteObject` on those keys to every credential, operators included. The model keeps F1 as a documented fixture, and its G6 check runs without the administrative deletion (case C0).

## D15. No read lease and no stale local read in v1

Every strong read revalidates the head with the D7 conditional GET, about 10 ms to fr-par from a warm owner, because that request is what keeps a read from returning data that a takeover has superseded. A lease would remove the request but make safety depend on bounded clock drift and pauses, and a "maybe stale" local read would add API surface that PLAN §2 explicitly does not provide. Both can be added later without changing the storage format.

## D16. Small writes publish in one CAS: an inline tail in the head

A write that uploads an object and then CASes the head makes two sequential S3 round trips, and each is exposed to the rare multi-second PUT stalls measured on Scaleway. The head therefore carries `tail`: at most one LTX delta, inline (base64), covering the sequences after the last delta ref up to `head.sequence`. Each mutation compacts `tail + new delta` into one LTX with the existing compactor (later page wins). If the result is at most `InlineBytes` (31 KiB raw, so the largest valid head stays under 64 KiB) and the head already references an object with `base_revision >= 1`, the mutation is a single CAS carrying the new tail. Otherwise it PUTs that compacted LTX as an ordinary delta object and CASes the head with the ref appended and the tail empty, which is today's path and doubles as level-0 compaction.

Rules, enforced by `head.Validate`:
- A tail is allowed only when some ref has `base_revision >= 1`. The first mutation of an incarnation therefore always uploads an object, which keeps D5's resume check complete: a used-then-deleted head always leaves a base >= 1 object behind.
- The tail is the last link of the chain (contiguous range ending at `head.sequence`, sha256, pre/post checksums), and the replay bound counts its decoded pages.
- A successor with an unchanged sequence carries the tail byte-identical.
- Snapshots empty the tail. Run compaction of delta refs carries it unchanged.

Resolve, GC and the 32-ref cap are unchanged: the tail is never an object and is always replaced together with the head, so a single-CAS mutation resolves through the receipt in the head. Capture must emit every page a delta grew the database by, because compaction is exact only then (asserted in the engine).

## D17. The inline tail keeps its 31 KiB threshold despite the head bytes it carries

Every inline mutation re-uploads the whole tail inside the head, so a 100-byte write uploads about 29 KiB of head on average (M6 `TestAmplification`, 2,000 mutations of a 1 MiB entity). Lowering the publish threshold below the format maximum was measured with the same fixture:

| Inline threshold | Head KiB/mut | Object KiB/mut | Total KiB/mut | PUT_IMM/mut | Single-CAS writes |
|---|---|---|---|---|---|
| 31 KiB (D16) | 29.4 | 2.9 | 32.3 | 0.05 | 95% |
| 16 KiB | 17.5 | 5.0 | 22.5 | 0.16 | 84% |
| 8 KiB | 9.2 | 14.0 | 23.2 | 0.85 | 26% |
| 4 KiB | 7.6 | 16.1 | 23.7 | 1.14 | 0% |

Total upload bytes fall by at most a third, because the bytes move into delta objects and compaction, while every write that leaves the inline path pays a second sequential S3 round trip and its stall exposure. Scaleway bills requests, not ingress bytes, and the measured cost of the larger head on fr-par is a few milliseconds (small update p50 38 ms against 35 ms for a raw 4 KiB CAS, docs/PERFORMANCE.md). The threshold therefore stays at the format maximum. PLAN §18.3's upload-bytes gate is evaluated on this fixture as measured, and it is the gate to revisit if a provider bills ingress.

## D18. Group commit is kept: queued Updates of a hot entity share one publication

M7 measured the hot-entity case first (`qual stress --hot`, docs/PERFORMANCE.md): with `BatchMax` 1, one entity sustains one head CAS round trip per update whatever the number of clients (MinIO 335-339/s, MinIO +25 ms 28-29/s, Scaleway fr-par 21-24/s for 1, 8 and 32 clients), and queueing alone makes the 32-client p50 1.06 s at +25 ms and 1.42 s on Scaleway. With `BatchMax` 16 and the same payloads: 8 clients 1,378/s, 117/s and 93/s; 32 clients 1,992/s, 199/s and 170/s (4-8x; run-to-run noise is up to 10%: the new binary with `BatchMax` 1 measured 365-374/s on MinIO against 335-339/s before the change, with identical request counts, and matched within 3% at +25 ms); 32-client p50 132 ms (+25 ms) and 137 ms (Scaleway); one client unchanged. Measured batch sizes are min(clients, 16).

The optimization is therefore kept, as PROTOCOL §6 "Batches" specifies it, opt-in at first (`BatchMax` stayed 1 by default, PLAN §11.4; on by default since the last amendment below):

- The batch is formed by the existing entity mutex, with no new goroutine: an Update that finds the entity busy joins a FIFO queue while it waits; the writer holding the mutex, after its own local commit, runs queued Updates' transactions itself, in order, with consecutive sequences, while only queued Updates wait (a queued read, Lookup, Migrate or ownership operation stops the batch: PLAN §6.5's barrier rule, applied conservatively). One capture, one delta (inline tail or upload), one CAS.
- Every outcome that observed unpublished state is held until the publication resolves: callback errors, admission verdicts (including a replay or `id_conflict` against an earlier unpublished member) and results. Not committed → `outcome_unknown` (unknown) or `unavailable`/the definite code (definitely not), with each member's own ID. A publication proven only through the leader's receipt (the request may have committed through another publication) is re-checked per member by receipt. While unresolved, every member's ID gets `outcome_unknown`.
- The upload uses the node-owned commit context, so the leader's deadline cannot abort the others; a member canceled after it was taken gets `outcome_unknown` at once and Lookup resolves it.
- `BatchDelay` is not used: only already-queued Updates are taken, so a lone writer pays nothing. Amendment (after M7): `BatchDelay` is removed from `Limits` with its validation, because an unused knob is API debt; batching takes already-queued writers only.
- `Stats.Batches` (new, amends the PLAN §11.4 Stats shape) counts committed mutation publications by member count, so deployments report actual batch distributions.

Cost: +183 nonblank noncomment production lines in the root package (2,233 → 2,416; ops.go 599 → 773). Safety evidence (both `BatchMax` 1 and 16): root suite, race lane, MinIO root suite, kill harness at `GARDEN_KILL_RUNS=10` with batching on; new tests `TestBatchMembers`, `TestBatchUnresolved`, `TestBatchCancellation`, `TestBatchNeverPassesRead`, `TestBatchHotLedger` (16 writers on one entity under lost CAS replies and unknown-outcome windows; ×30, race ×5, MinIO ×3). The internal model still has one operation per publication; see .work notes before extending it.

Amendment (default on): `BatchMax` now defaults to 16, the qualified maximum (`Limits{BatchMax: 1}` keeps the unbatched path; a single writer is unaffected, since only already-queued Updates are taken). Evidence: `TestBatchKill` (one entity, 8 clients, SIGKILL at the 12 leader-path failpoints and at `sql.member`, a new failpoint inside a member's own transaction in `collect`, where the killed batch is still being assembled), with partial batches mixed into the workload: members whose callback writes then fails, a member reusing an acknowledged ID with another input (`id_conflict`) and one replaying it; every first answer was the final outcome, `unavailable`, `outcome_unknown` or none, and every non-final one reached its final outcome on retry after the restart, with the ledger checks unchanged; routed histories across node processes with batching on (`TestRoutedHistories` with `GARDEN_TEST_BATCH`, linearizable); the internal model's batch rule (one publication, several operations) lands in parallel. The root suite runs batched by default and unbatched with `GARDEN_TEST_BATCH=1`.

## D19. SQLite extensions: built-in modules and Go extensions, no native code

The library replicates pages, not SQL, so any extension whose state lives in the SQLite file replicates, compacts, exports and survives takeover with no extension-specific code. Native C extensions (`load_extension`, shared objects such as sqlite-vec) are impossible in pure Go (PLAN §12.2) and stay denied.

- **Built-in modules.** The embedded SQLite is compiled with FTS5, R*Tree, Geopoly, JSON and math functions (`research.lock.json`). Application SQL may `CREATE VIRTUAL TABLE` (mutation mode) with `fts5`, `fts5vocab`, `rtree`, `rtree_i32` and `geopoly`; `dbstat`, `sqlite_dbpage` and every other module stay denied, and so do reserved names (a table named `_state` would own `_state_data`). The modules' own statements on their shadow tables pass the authorizer like application SQL; defensive mode, not the authorizer, keeps the shadow tables read-only, undroppable and unalterable to application SQL and refuses triggers on or writing to them (`TestBuiltinVirtualTables`). fts5 queries `PRAGMA data_version` and rtree `PRAGMA page_size`: both are allowed without argument. rtree and geopoly prepare their shadow writes when they connect, which can first happen in a read (a fresh activation or a schema reload), so read mode authorizes writes to `*_node`, `*_rowid` and `*_parent` tables and `Read` now also sets `PRAGMA query_only=ON`, which refuses every write at the engine level (PLAN §6.1: read-only by authorization and SQLite state). Reserved names had one gap, older than this decision: `ALTER TABLE x RENAME TO _state_y` passes only the old name to the authorizer, and renaming an fts5 or rtree table renames its shadow tables too. Mutate now checks `sqlite_schema` after the callback and rolls back with `engine.ErrReserved` (`invalid_argument`, the cache discarded like any library failure) when a table other than `_state_meta`/`_state_receipts` has a `_state_` name, or is named `dbstat` (`sqlite_*` names are refused by SQLite itself) (`TestRenameIntoReserved`). The authorizer does not see `REFERENCES` targets either, and a foreign key from an application table to a reserved table (`CREATE TABLE pin(x REFERENCES _state_meta(sequence))`, or `ALTER TABLE ... ADD COLUMN`) would commit and then fail every later mutation in the library's own receipt prune or meta update, before the callback could drop it ("foreign key mismatch", or a cascade into application rows): the same post-callback check rolls back any foreign key whose target is reserved (`pragma_foreign_key_list`), names compared in Go, not with SQL `LIKE`. `REINDEX` passes the authorizer the name of the index it rebuilds, `sqlite_autoindex__state_receipts_1` for the receipts key: `reserved()` covers `sqlite_autoindex__state_*`, and the authorizer answers `SQLITE_IGNORE` for it, so `REINDEX _state_receipts` rebuilds nothing and a bare `REINDEX` still rebuilds the application's indexes. Activation refuses an image holding either (`corrupt`: the library never publishes one, so it comes from an import) (`TestForeignKeyToReserved`). An external-content fts5 table may name a reserved table as its content: the fts5 statements that read it are denied. An fts5 index put out of sync with external content by a wrong `'delete'` command is the application's state: `integrity_check` at activation does not compare external content (`TestFTS5OutOfSync`), and fts5 reports inconsistencies it meets at write time as an SQL error of that statement.
- **Go extensions.** `Config.Extend func(*sqlite.Driver) error` is called once by Open on a private `*sqlite.Driver` of the Node, which opens every entity connection (`sql.OpenDB`), so its registrations reach no other connection in the process (PLAN §6.1). An error fails Open with `invalid_argument`. The modules it registered are allowed besides the built-in ones. Extend must not replace a function or module a fresh driver has (any arity of a function name counts; `json*` and `pragma_*` module names too, which SQLite registers on first use) nor register a module with a reserved name: modernc replaces a built-in silently, and a replaced `upper()` would break activation of an image using it in a CHECK constraint or an index, a Go module named `fts5` would run caller code at activation, and a replaced `like()` or `lower()` would skew the library's own SQL (its reserved-name checks now compare names in Go anyway). A registered collation fails Open, because indexes and columns can use a collation whatever `trusted_schema` says, so activation would depend on caller code (and a changed or replaced `nocase`/`binary` makes index lookups wrong and `integrity_check` call a valid image corrupt). A connection hook would run caller code on every connection outside the authorizer, so it fails Open too. modernc keeps a driver's registrations in unexported fields and offers no listing (a replaced name looks unchanged in `pragma_function_list`), so `NewDriver` reads them by reflection and fails on an unknown driver layout, which a modernc upgrade would show in `TestExtendReplacesBuiltin`. Contract: durable state only in the SQLite file, a Go module keeps none elsewhere. `trusted_schema=OFF` and modernc functions not being `SQLITE_INNOCUOUS` refuse caller functions in index expressions, generated columns and CHECK constraints when created, and in views and triggers when used, with "unsafe use of f()"; Go modules' tables likewise in views and triggers (`TestGoExtensions`). `PRAGMA integrity_check` connects every virtual table whose module is registered, so activation runs it (and the metadata check) on a second, read-only connection from a driver without the Node's extensions: a module whose `Connect` fails cannot make activation fail, and activation never runs caller code (`TestActivationRunsNoModuleCode`). So an entity using an extension needs it only on Nodes that run the queries calling it: activation and `integrity_check` succeed without it, and a missing function or module is SQLite's error to the callback, never `corrupt` (`TestExtensionsDurable`). Package-level modernc registrations by other code in the process are visible on every connection modernc opens; a name both register resolves to the package-level one, so the allowlist excludes names present on a fresh driver.
- **Vector search.** Package `vec` (`vec.Register` for `Extend`) provides `vec_f32`, `vec_distance_l2`, `vec_distance_cosine`, `vec_dot` and `vec_length` over little-endian float32 BLOBs, the float32 format of sqlite-vec, so stored vectors stay readable by sqlite-vec elsewhere. KNN is `ORDER BY vec_distance_cosine(col, ?) LIMIT k`, a scan as sqlite-vec's `vec0` does. `BenchmarkKNN` (k = 10, cosine, one entity, in-memory store, i7-10510U, `CGO_ENABLED=0`): 384 dimensions 10k rows (20 MiB) 16.0 ms, 50k (98 MiB) 81.7 ms; 768 dimensions 10k (39 MiB) 30.1 ms, 50k (196 MiB) 147.3 ms per query. About a third of the time is the distance loop, much of the rest is SQLite's row scan and page reads (the engine's page cache is 1 MiB, so a scan rereads the file from the OS cache).

Cost: +9 nonblank noncomment production lines in the root package (2,408 → 2,417), +83 in `internal/engine` (1,018 → 1,101), 110 in `vec`. The review fixes (foreign keys to reserved tables, no replaced built-ins, activation on an extension-free connection, `REINDEX`): +39 in `internal/engine` (1,101 → 1,140).

## D20. Public API amendments from M9

M9 built two examples (`examples/counter`, `examples/kvregistry`) on the public API only; these are the amendments their findings required.

- **The stored schema on `schema_mismatch`.** A caller had no way to learn an entity's stored schema, so a rolling upgrade had to guess whether to `Migrate` (the entity is older than the code) or defer to a newer Node (the entity is newer). `Error` gains one field, `Schema uint32`, set on every `schema_mismatch`: the stored schema for `Read`, `Update` and `Migrate` (with `At`, the version at which it was observed), the archive's schema for `Import`. A Node learns it from the call it was making anyway, under ownership, so it is never stale; `Route` stays an ownership observation (adding the schema there would make a `Migrate` look like a route change to `Takeover`). (`TestSchemaMismatchReportsStored`.)

- **Collect after maintenance.** The owner runs `Collect` on an entity after each committed compaction or snapshot, outside the gate, best effort: superseded objects were the largest line of the Scaleway bill (docs/COST.md) and otherwise waited for a caller's schedule. One head GET and one LIST per maintenance step (about one per 8 uploaded deltas); explicit `Collect` keeps its role for abandoned uploads.
- **No `Error.RetryAfter`.** PLAN §11.4 lists it as a hint, but the library never set it (2026-11-10 review): a field that is always zero invites callers to sleep zero. Retry pacing is the caller's (`examples/kvregistry` waits 100 ms before retrying with the same ID). Removed before release, while removing is free.

Cost: +3 nonblank noncomment production lines in the root package (2,418 → 2,421).

## D21. Warm tier: a settled entity parks its file instead of deleting it

S3 holds the state; the local cache only saves downloads. An entity has three states, none of them a new flag (D8): **hot** (`e.db` open), **warm** (a file `CacheDir/warm/<namespace>/<EntityDir hash>.db` with a `.json` hint: the image it holds and the replay pages of the links it was parked with), **cold** (nothing local).

- **Park.** Where an idle, settled entity used to be discarded (the `IdleTimeout` sweep, the `ResidentEntities` and `CacheBytes` sheds, `fetch` finding a newer or no longer owned head, `Close`), `park` checkpoints the published image into the main file (empty WAL), closes the database, renames the file into the warm tier and writes the hint. Anything unsettled, speculative or failing is still a D10 discard; `Evict` still deletes, and also drops the warm file, so it forces a cold activation.
- **Activate.** Before the object GETs of §4, `warmStart` moves the key's warm file into the session dir (a rename: safe across processes sharing a `CacheDir`) and picks the first link of the current head whose `max_sequence` exceeds the file's sequence. None: the file is at the head, no GET. The snapshot: the file is older than the snapshot, cold. Otherwise it GETs only that link and the later ones and restores from the file with `engine.Restore(..., from)`: an LTX delta `[a..b]` carries the final content of every page written in `[a..b]` and every page it grows by, so applied onto any image at `s` in `[a-1, b-1]` it yields the image at `b`; only the first link's "follows" check is relaxed to that range (`apply`, `overlay`). The final gates are those of a cold restore, unchanged: page count and full-file checksum equal to the head's, `_state_meta` equal to the head (namespace, key, incarnation, schema, sequence), `integrity_check` on an extension-free connection. A file that is not what its hint says, of another incarnation, torn, or corrupted fails them, is deleted, and the entity activates cold. The head GET is the one every activation does; a 304 would need the decoded head in memory, which a warm entity does not have.
- **Budget.** Warm files count in `CacheBytes`; `fit` deletes the least recently used warm file before parking a resident entity. Unaccessed entities therefore move to S3 only as other entities need the space. The tier survives restarts: Open indexes it and removes anything without a readable hint.
- **Crashes and failures.** A kill while parking leaves a file without hint (removed at the next Open), or a file another process replaced under a hint it no longer matches: the overlay's rolling checksum starts from the hint and misses, and the final gate re-derives everything from the file. After the claim, the file lives in the session dir, which the next Open deletes with the dead session; catch-up never writes under `warm/`. A store failure while fetching the links puts the file back (only a missing or corrupt object, or a failed gate, deletes it), and `fit` never evicts the warm file of the entity it is making room for. `TestWarmKill` (killnode): 20 runs each of a SIGKILL inside `park` at Close, after the claim, and 0-3 ms into the overlay, plus 20 control runs that must activate warm; every run reads exactly the committed rows.
- **Pages.** The replay pages of the links before the overlay come from the hint, keyed by object SHA-256; a link the hint does not know (compacted elsewhere since) sends the activation cold rather than guess the snapshot heuristic's input. A `CacheDir` shared by several processes is safe (claims are renames, every file passes the gate) but each process budgets the shared tier as its own.
- **Review.** An adversarial review (Fable, 2026-11-10, `.work/FABLE_D21_REVIEW.md`) found no safety defect; its liveness findings (a warm file evicted by its own activation, a transient store error deleting the file, a hint removed without owning it) are fixed above.
- **Stats.** `WarmHits`, `CatchUps` (activations from a warm file as is, or caught up), `ActivationBytes` (object bytes GET by activations, cold and catch-up), `WarmEvictions`, and the gauges `WarmEntities`, `WarmBytes` (also in `CacheBytes`). `Activations` stays the total.

## D22. Format 1 amendments from the consumer-side review (2026-11-10)

A review of the public API from outside (`.work/paradigm-probe.md`) measured what consumers pay; these change format 1 before anything uses it, or a default.

- **Receipts are a rowid table keyed by sequence** (`sequence INTEGER PRIMARY KEY, operation_id BLOB NOT NULL UNIQUE, input_hash, result`). The `WITHOUT ROWID` layout was an index b-tree whose leaf keeps at most 1,002 bytes of a row: any result above ~940 bytes paid a 4 KiB overflow page (4,686 bytes per receipt from 1 KiB to 4 KiB results). A table b-tree leaf keeps 4,061 bytes; sequences are monotonic, so inserts append. `TestReceiptCost`: 113, 389, 1,413 and 4,137 bytes per receipt for 0, 256, 1,024 and 3,900-byte results (page packing plus the operation-ID index). Activation compares both library tables' `sqlite_schema.sql` with the format 1 DDL, so an image in another layout is `corrupt` (`TestOldReceiptsLayoutRejected`).
- **`ResultBytes` defaults to 4 KiB** (was 16 KiB) and bounds stored results only (Create, Update, Migrate, Import): a receipt is a result's whole cost, and at the default 1 h retention a 64 MiB entity holds about 18.6 KB/s of results. **A Read result is unbounded**: a Read stores nothing, and the bound was bypassable through a captured variable anyway.
- **`secure_delete=FAST`** on every connection: deleted bytes leave the image, its delta and later snapshots at the deleting commit (`TestSecureDelete`); with `auto_vacuum=FULL` no page is added to a delta.
- **Clock guard.** One write from a node whose clock ran 48 h ahead moved the durable receipt floor 47 h ahead: every ID from a correct clock then got `id_expired`, on every node. The S3 adapter now samples the store's clock from the `Date` header of every reply (a deserialize middleware in the per-call options); a mutation (Create, Update, Migrate, Import, batch members) on a node more than 5 min off is refused as `unavailable` before any local change, after one namespace GET re-samples. Reads are unaffected. A store that sends no `Date` disables the guard (`TestClockGuard`).
- **Entities being built count as resident.** `room` counted a busy entity only once it had a file size, so concurrent creates and activations all passed on the same count (64 files for `ResidentEntities` 16 in `TestResidentBoundUnderConcurrentCreates`; 269 residents for 256 in the review). An entity is counted from `room` until `unreserve`, and its size is recorded before.
- **Fail fast behind an unresolved publication.** An operation that is not the unresolved candidate's own retry settles it for at most one `StorageAttemptTimeout`, at most once per that timeout, then returns `unavailable`; the candidate's own retry still waits up to `CommitTimeout`. During an outage the second and later operations on the entity no longer block 10 s each (`TestOutageFailsFast`: under 1 s, then under 50 ms).
- **Erasure: `Snapshot(ref)`.** Old objects were purged by write volume, never by time, so a deleted row's history lingered in superseded deltas. `Snapshot` publishes the current image as a snapshot and collects everything it supersedes; with `secure_delete`, a deleting Update followed by `Snapshot` leaves the bytes in no stored object (`TestSnapshotErases`, with a control showing them stored before). It uploads the whole database. A replaced `head.json` takes its inline tail with it, so bucket versioning must be off, or noncurrent versions must expire, for erasure to hold.
- **`Scan(ctx, afterKey)`** yields the `Route` of every entity, in key-hash order, resumable from the last key: one LIST per 1,000 stored objects and one GET per entity, with no knowledge of the key layout outside the library (`TestScan`).
- **Entity size.** `PRAGMA page_count` and `PRAGMA freelist_count` are allowed in application SQL, reads and mutations alike (`TestEntitySizeVisible`); receipt bytes stay a documented estimate (result + ~80 bytes per receipt for `ReceiptRetention`).
- **Large entities keep the 64 MiB default.** Measured on a 48 MiB entity (local RustFS): a snapshot (encode, PUT, CAS, Collect) takes 1.0-1.2 s under the entity's gate, of which encoding is ~0.5 s of CPU, mostly SHA-256 and LZ4 (reading pages through `sqlite_dbpage` is 7% of it, so encoding from the main file would not pay); one-row updates between snapshots stay under 15 ms. Nothing of it can leave the gate: an object published after the head moved would race every node's automatic Collect. The stall law to plan for: one snapshot per ~`page_count` rewritten pages, each ≈ size / (hash + compress + upload throughput); on Scaleway add ~0.5 s per 48 MiB of upload.


## D23. Shared head validation by issue time; reads ride a batch's CAS

PLAN §7.3 lets reads queued before a validation GET share it, and §6.5 stops a batch at a queued read. The review measured the cost of doing neither: on one entity 16 concurrent readers got the throughput of one (98/s, p50 163 ms, RustFS with replies delayed 9 ms per GET and 35 ms per PUT), and 8 writers with 8 readers made 19 writes/s and 19 reads/s at p50 423 ms against 168 writes/s for the writers alone, because every waiting read broke group commit.

- **One timestamp.** The entity records `valid`, the monotonic issue time of the request that last proved its cached head current: the conditional GET (200 or 304) of a read, a barrier or a takeover, the CAS of a committed publication, or the resolve GET that settled one; it is cleared with the head. An operation invoked at `t0` skips its head GET iff `valid > t0` and the local image is exactly the head (`Published() = imageOf(H)`, set only by the restore gate or by the checkpoint of a committed candidate). Proof: the GET or 304 proves `H` current when it is answered, the CAS when it applies, both inside `[t0, now]`; the answer then comes from an image that was the head during the call, the §7.3 linearization argument unchanged. Read, Lookup, Export and the §0 barrier (replays, `id_conflict`, `schema_mismatch`, callback errors) use the rule.
- **Reads ride a batch.** A Read waiting on the entity is counted in `readers`; a batch leader takes queued Updates while every other waiting operation is a Read. The read was invoked before the batch's CAS was issued, so the committed CAS proves the state it then reads; if the publication ends unresolved or not committed, nothing set `valid` and the read does its own GET (behind an unresolved candidate it gets `unavailable`, §2 rule 5). A queued Lookup, Migrate, Create, Import, Release, Evict, Export or Takeover still stops a batch. This amends PLAN §6.5's "do not pass a queued read": the read is not passed, it answers from the batch's committed state.
- **Model.** A read may be the queued member behind an Update (case BR): on the leader's committed outcome it answers from the node's image if that image is the proven head, otherwise it runs on its own later. BR explored completely (58,177,750 states, no violation); the control `read-rides-unresolved` (the read answers from the candidate after `outcome_unknown`) fails G2 in 3 steps.
- **Measured** (the review's `reads` probe, same setup): 16 readers 1,409/s at p50 10.7 ms (one reader: 98/s, 10 ms); 8 writers + 8 readers 168 writes/s and 173 reads/s at p50 45 ms, in 8-member batches. Tests: `TestSharedValidation` (16 reads behind an in-flight GET: 2 head GETs; behind a publication: none), `TestReadRidesCAS` (8 writers, 8 readers, linearizable counter reads, batches of 8), `TestBatchNeverPassesRead` (the queued read sees the batch's state with no head GET).

## D24. Strong reads on any node; reads never take over

PLAN §7.3 has a read verify the owner, and D4 let a Read or Lookup take over from an earlier session of the same NodeID. Neither is needed for a strong read: it publishes nothing and returns nothing the head does not name, so what makes it strong is a head proven current by a request issued after the call began (D7, D23) and an image exactly equal to that head. The image is either a file whose published image equals the head's (set only by the restore gate or by the checkpoint of this node's own committed candidate, both exact) or a fresh activation of exactly that head. Ownership only let the owner skip that comparison.

- **Read, Lookup and Export run on any node** and never CAS. `not_owner` is a mutation's answer only; D4's implicit takeover is mutation-only (Update, Migrate). An Update on a non-owner still gets `not_owner` with the Route.
- **A follower keeps its file.** A local image of a head this session does not own stays resident, counted in `ResidentEntities` and `CacheBytes` and parked by the cache policy like any other. `fetch` parks it (D21) when the new head has another image or the same image through other links (another node's compaction or snapshot: the replay page counts of the new links are unknown); the next activation then catches up from the parked file through the D21 warm path (newer links overlaid, full checksum and `integrity_check` gate). That gate is a follower's cost per change of the head, not per read: a read of an unchanged head costs one 304 or none (D23). Deviation from the review memo, which had `leave` park an unowned head: parking at every `leave` would make every follower read pay the restore gate (a rename, a full checksum and `integrity_check`) even when nothing changed.
- **Model.** The read branch lost the D4 takeover and the `not_owner` finish: any node activates the head it read and reuses its image only when equal. Case F (three nodes; n2 owns nothing and reads twice under updates, a takeover, a compaction and a collection): complete, 25,997,217 states, no violation. The control `follower-stale-read` (a follower reads its local image without comparing it to the head) fails G2 in 7 steps.
- Tests: `TestFollowerRead` (7,643 reads on a node that never owns the entity during 1,600 writes with compactions, snapshots and collections: all linearizable, sequences monotonic, zero owner changes, one catch-up per change: 402 activations, 393 catch-ups; Lookup works, Update gets `not_owner`), `TestExportFollower` (a lagging follower exports the current head, Import accepts it); the routed histories send half of their reads to any member, checked linearizable. Assertions that a non-owner's read is `not_owner` (`TestRestartRecoversEverything`, `TestOwnershipAndMigrate`, killnode `TestConcurrentTakeover`) now assert that the read answers the current state and the owner is unchanged; `TestEntityMapBounded` misroutes Updates instead of reads.

Amendment (`PendingPerEntity` 64 → 256): with shared validation a queued read costs one SQL transaction, and 256 queued writes are 16 batches, about 0.6 s on Scaleway, the wait 64 queued reads used to cost. 100 reads at once on one entity: 35 `capacity` rejections at 64, none at 256 (3,924/s, p50 23 ms, review probe; `TestHundredReaders`).

## D25. Delete leaves a tombstone head; recreation is a CAS on the tombstone

PLAN had no deletion, and deleting `head.json` is outside the store contract (D14). `Node.Delete(ctx, ref)` (review memo A4, `.work/FABLE_REVIEW_DESIGN.md`) ends `ref`'s incarnation and keeps the key's head for ever, as a tombstone.

- **Format.** `head.deleted`, always encoded. A tombstone has no owner and no tail; its refs, sequence, schema and checksum are its predecessor's, and nothing it names is live. `Successor`: a tombstone replaces an owned head like a release (owner null, epoch+1, revision+1) with its refs unchanged and the tail dropped; only a recreation replaces a tombstone: a new incarnation's genesis (one snapshot, no deltas, no tail; sequence 1, or Import's exported+1) at revision and epoch +1, its snapshot produced at base the tombstone's revision. Revisions stay monotonic across incarnations, so no-resurrection and Collect's `base < R` are unchanged. A tombstone after a tombstone, or any other successor of one, is refused (`TestTombstone`).
- **Delete** runs on the owner like a mutation (D4's implicit takeover included; `not_owner` elsewhere): settle, publish the tombstone, drop the local image and the warm file, leave the gate, then Collect against the tombstone: everything of the incarnation has `base < R` and nothing is live, so one pass erases it. A Delete that finds its incarnation deleted already collects it again and returns nil, so a retry after any failure (a kill after the CAS or inside the Collect) finishes the erasure. A lost Delete is done iff the head it finds is a tombstone or another incarnation; the release rule (done iff not owned) would call a Delete beaten by a takeover done.
- **Every other operation** answers `not_found` on a tombstone of its Ref's incarnation (after the incarnation check): Read, Lookup, Update, Migrate, Export, Snapshot, Takeover, Release, Resolve. Scan skips tombstones; Collect accepts one. A node that sees a tombstone drops its local image and warm file; another node's warm file fails the D21 gate (incarnation) at its next activation of the key, or stays until `CacheBytes` evicts it if the node never touches the key again (OPERATIONS.md).
- **Recreation.** Create and Import on a tombstone first Collect it (Collect lists only the head's incarnation, so a Delete cut before its Collect would otherwise leave the old objects for good), then build the genesis of a new incarnation with no birth PUT and publish it with the tombstone as base (`If-Match`), not `If-None-Match: *`. `birth.json` stays the first incarnation's; with a head present there is no birth-without-head window, so D5 and its `outcome_unknown` rule do not apply. Create on a live head now decides by the receipt of its ID in the current state (any node, D24), not by `birth.json`, which does not name a recreation's create: replay or `id_conflict` by bound, otherwise "key exists".
- **D14 strengthened.** A key that ever had a head keeps one: `If-None-Match: *` can never apply again, so the library never needs a head deletion and finding F1 stays outside it.
- **Receipts end with their incarnation.** A request retried after the Delete is `not_found` (its Ref), or for Create and Import a recreation: PLAN §8's "never delete a receipt while accepting its ID" holds per incarnation. A caller that may redeliver a Create after a Delete uses a fresh key or checks first (doc.go).
- **Deviations from the memo**, all found while modelling or implementing: (1) the tombstone drops the inline tail instead of carrying it byte-identical, or the last ≤ 31 KiB of writes would stay in `head.json` for ever (Validate skips the chain's end check for a tombstone); (2) resolving a candidate with an operation across a deletion: its receipt cannot be read in a tombstone (whose objects are being collected: hydrating it could leave the candidate unresolved for good), and its absence from another incarnation proves nothing, since the candidate may have committed in the deleted one. It is not committed only if the new head took the candidate's own revision (`cur.revision = base.revision+1`), otherwise the outcome is unknown for good (discard, `outcome_unknown`, nothing left unresolved), like a receipt past the floor; (3) a lost Delete is done when the head is another incarnation too, not only its own tombstone; (4) recreation collects the tombstone first; (5) a recreation's sequence may be Import's.
- **Model.** `Head.Deleted`, an incarnation ordinal `Gen` that a request's Ref names (`incarnation_mismatch`, `not_found`), `kDelete` with its Collect inline, recreation as a CAS on the tombstone. New checks: G6 "no genesis applies by If-None-Match on a key with a head" and "a tombstone is replaced only by the genesis of its create alone, at revision and epoch +1, snapshot at base the tombstone's revision"; G1 scoped to the acknowledged incarnation; `not_found` only if the request's incarnation was a tombstone during the call; a Delete acknowledged only once its incarnation is gone; a tombstone's image is never a state a read may answer from, and its refs are not live (G8). Cases, explored exhaustively with no violation: D (delete vs update, a follower read, a takeover, a crash, a hedge: complete, 34,392,848 states), DT (delete vs takeover: complete, 9,909,665), DU (an update resolved across a deletion and a recreation: complete, 126,270) and DR (two recreations racing, the new and the old Ref: 150,000,000 states, budget-bounded; an earlier, wider D and DR also ran 150,000,000 each without a violation). The existing cases still pass on the changed model (Create on a live head now hydrates for its receipt instead of reading birth.json, which enlarged them): C0 complete 94,713,551, CD complete 99,377,480, G complete 3,857,008, I complete 13,722,739, B 150,000,000 budget-bounded. Controls, each caught by a minimal counterexample: `delete-done-as-release` (DT, 6 steps), `receipt-across-incarnation` (the memo's receipt check; DU, 17 steps), `recreation-keeps-data` (DR, 6 steps).
- Tests: `TestTombstone` (head rules), `TestDelete` (every operation `not_found` on the owner, a follower and a warm node, whose image and warm file are dropped; only `birth.json` and `head.json` left; idempotent; Create recreates with a new incarnation and nothing old, `birth.json` untouched, revision and epoch carried on, the retried Create replays, the old Ref gets `incarnation_mismatch`; Import on a tombstone), `TestDeleteFollower` (a follower reading during 40 writes and the delete: monotonic, then `not_found` for good), `TestDeleteKill` (killnode, `GARDEN_KILL_RUNS` runs, default 10, each of a SIGKILL after the tombstone CAS and before the Collect's second deletion; the retry from the restarted node, and a second one, return nil and leave only birth and head).

Final review (Fable, 2026-11-10, `.work/FABLE_FINAL_REVIEW.md`) of D21-D25 together; fixed:
- **An activation's collection-race re-read now checks for a tombstone** (`not_found`): a follower whose object GET missed while the owner deleted would otherwise restore the dead incarnation from the tombstone's refs (`TestDeleteReviewCases`: `state_missing` before, `not_found` now).
- **The old Ref of a recreated key still collects and deletes**: `Collect` reaps another incarnation than the current one entirely (revisions are monotonic across incarnations, so it ended below the current revision), and `Delete` treats `incarnation_mismatch` like `not_found`.
- **`Delete` reaps against the settled head**, not its own proposal, and **needs no activation** (`ownedHead`): a cold or damaged entity can be deleted.
- **A mutation deleted under it is `not_found`**, not `not_owner` with an ownerless Route.


## D26. kit: backup, a reference router and durable wakes, on the public API

The kit design (`.work/FABLE_KIT_DESIGN.md`) needs nothing from the core, so package `kit` uses only package garden's exported API, and the core imports nothing from it.

- **Backup and Restore.** `Backup` writes every live entity's `Export` (Scan, tombstones skipped) into one tar, a member per key (hex of the key); `Restore` imports each member whose key has no head, with the schema from the export's manifest and a request hashed over the archive, so a second Restore imports nothing and a deleted entity stays deleted. `TestBackupRestoreDrill` is the namespace drill (20 entities, one deleted, restored into another prefix with identical state).
- **Router.** Mutations travel by name (`Call{Op, Key, Req, Input, Create}`; a `Handler` registered under `Op` on every Node), so `Call` and `Reply` are plain data. Routing is sticky to the owner last seen (one `Resolve` on a miss); a takeover happens only on the Node `Preferred` names, and only when the owner is absent from `Membership` or the entity is unowned: no rebalancing of live owners, so a false suspicion costs one takeover and never a stale publication (the core fences it). A forwarded Call is never forwarded again (`Serve` answers `not_owner` with the Route), every attempt carries the identical Request, `route_changed` and `not_owner` back off with full jitter, four attempts at most, and a transport failure on the last one is `outcome_unknown` for the request's ID, since the remote owner may have committed it. Reads need no router (D24). Tests: `TestRouter` (a counter exact across 40 mutations from three Nodes, the owner never changes while it is a member, the Preferred member takes over once after the owner leaves), `TestRouterTransportLossIsUnknown`.
- **Wakes.** Shard entities `kit/wakes/<i>` hold only `(key, due, armed)` rows; what is due, and what to do, lives in the woken entity, written by the business mutation itself, so a wake is idempotent by construction: the handler acts on the entity's own due rows and returns its next time (and, D29, a result for a hook). Arm comes before the mutation that needs it (a crash in between costs a spurious wake, never a lost one); an earlier arm wins. `Run` on every Node fires the shards `Preferred` puts on it: it wakes each due key through the router (a deleted key is skipped), then sets the row to the handler's next time, except that a row armed within `grace` (15 min: a business mutation that had not committed yet, plus D22's skew) stays, due at most at its arm plus grace. A wake is at least once, at or after its time, while some Node runs `Run`. `TestWakes`.
- **Not built.** The directory (uniqueness claims) waits for a consumer that needs one.

## D27. Another request supersedes a create that left no object

D5 lets only the request named in `birth.json` finish a create, so a create cut between its birth and its head (a crashed process, a request ID past its retention) left the key `state_missing` for every other request. A consumer whose keys are deterministic (a uniqueness claim, a wakes shard) then loses the key. A Create under another request that finds `birth.json` without `head.json` and no object under the entity may now build genesis in a fresh incarnation, with no birth PUT (`birth.json` stays the first attempt's, as after a recreation, D25). No object means no head was ever published, since a head references its snapshot, so nothing acknowledged is replaced. The genesis CAS (`If-None-Match: *`) still admits exactly one create, and a create that loses it to another incarnation's genesis is not committed: that head is at the loser's own revision 1, so no delete can have come between, and the loser answers as for a live key ("key exists"), never `outcome_unknown`. A head absent over such a birth reads as `not_found`.

Once any object exists, the key stays `state_missing` for other requests. A single genesis snapshot left is ambiguous: the create may have stopped before its head CAS, or its head may have been published and then deleted (D14), or it may be what a Collect had not erased yet under a tombstone that was then deleted. The model refutes superseding it (case CD: an acknowledged genesis is replaced, G6) and republishing it (a deleted incarnation comes back, G6 and G8). Only the interrupted request resumes it (D5).

The model's genesis check now accepts a genesis in another incarnation than `birth.json`'s. A lost tombstone protects no data, and requests of a deleted incarnation are out of G1's scope. Control `supersede-over-objects` supersedes whatever objects exist, and the shortest search finds the G6 violation in case CD. Tests: `TestCreateAfterInterruptedBirth`, `TestCreateLosesGenesisRace`, `TestCreateResumeD5`.

## D28. A Create on a live key answers `exists`

"Key exists" was `invalid_argument`, the code of a malformed call, so a caller racing to create a key (a wakes shard, a uniqueness claim) could not tell losing the race from a bug without matching the message. It is now its own code, `exists`, with the Route of the live head, from Create and Import (and from a create that loses the genesis CAS, D27). `Wakes.Arm` relied on `id_conflict`, which a concurrent creation of a shard never returns: the losing create sees `exists`, or `state_missing` while the winner is between its birth and its head. Arm now retries its update on either, at most four times with the router's backoff, so the first arms of a shard from several Nodes all land. Tests: `TestWakesArmRacesShardCreation` (eight concurrent first arms from two Nodes; before, some failed with "key exists"), `TestErrorCodes`, `TestCreateIdempotentAndConflicts`.

## D29. Wakes: a handler result, a hook after recording, and a backoff on failure

A wake handler runs inside the woken entity's transaction, so it can claim due work (a row moving to a new generation, D8 style) but cannot perform an external effect, and `Run` fires a shard's keys one after another. The handler now also returns a small result, typically what it claimed. Once the wake is recorded in the shard, `Run` passes `(key, result)` to the `done` function given to `NewWakes`, which must not block: the caller performs the effect on its own pool, and one slow effect never holds the shard back. A handler that fails, or whose outcome is unknown, used to leave its row due, so it fired at every tick. Its row is now due again after `backoff` (1 min), still within the arm's grace window, and the handler stays idempotent by construction. Tests: `TestWakesResultAndBackoff` (the result reaches `done`; a failing handler runs once in 25 ticks, 26 times before), `TestWakes`.

## D30. The router remembers the routes it learns from a takeover or a create

A Node that took an entity over, or created it, did not record that it owns it, so every later mutation forwarded to it took it over again (a head GET each time). A route learned from a successful reply names only the owner: no epoch or revision. When that owner left, the Node `Preferred` names failed its first takeover as stale (`route_changed`) and spent one of its four attempts on it. `run` now remembers the route its takeover or create returned. Before taking over from an owner-only route, it resolves the head: it then takes over from the observed owner, runs the mutation if it already owns the entity, or answers `not_owner` with the route when a live member owns it. Test: `TestRouterTakeoverRoutes` (a takeover from an owner-only route failed `route_changed` before).

## D31. A Create is admitted at any age; only a tombstone refuses an expired ID

D27 frees a deterministic key only when its create left no object, and D5 lets only the create's own Request resume it, which admission refused once its ID was older than `ReceiptRetention`. A process killed between a key's snapshot and its head, and not retried within the hour, left the key `state_missing` for good: a wakes shard whose arms all fail, an address that can never sign in again. A Create is now admitted at any age (a future ID is still refused). No receipt can be lost on the paths that matter: `birth.json` permanently records the ID and bound a D5 resume must match, and a birth without a head never published a receipt to deduplicate; a fresh key has none; a live key answers from its current state as any create does (its receipt, or `exists`, also when this ID's receipt may have been pruned). Only a tombstone refuses an expired ID with `id_expired`: that request may have made the deleted incarnation, and a stale create must never recreate it. A recreation has no birth-without-head window (D25), so a deletable key recreates under a fresh ID without the risk D5 covers. The model drops the wall-clock admission of creates, answers `exists` on a live key whose receipt may be pruned (as the code already did) and `id_expired` over a tombstone; cases CA (CD with retention 2 and a clock jump expiring every ID, including the D5 resume over a genesis whose head was deleted at rest) and DA (a stale retry of the genesis request and another create after a delete, both possibly expired) are added. Test: `TestCreateAgedID` (a create cut before its head resumed with a two-hour-old ID by another process, a fresh key, a live key, a tombstone; before, the first create was refused `id_expired`).
